### Scope boundaries

- Do not re-implement response streaming, plaintext sendfile, static validators,
  or the full-body multipart parser. Extend them and close gaps.
- Do not raise a fixed capacity to make a benchmark pass. A larger limit is
  acceptable only after a probe shows the current bound is the measured cause.
- kTLS integration is not a 2.2.0 deliverable unless the pinned BoringSSL
  exposes a supported key-handoff path. The current standalone helper is a
  deliberate boundary; final disposition belongs to v3.5.0 SB-31.
- `io_uring_prep_splice` is conditional on a measured benefit. `sendfile` is
  already the zero-copy plaintext path.
- Cross-process listener handoff remains Task A-4 in section 15.
- The Zig 0.17.0 upgrade remains a 2.5.0 platform change.
- External-repository tasks (C1 host evidence and C3 adapter) cannot be closed
  by a library-only commit. Re-declare them with a dated restoration criterion
  if the host or adapter is unavailable.
- No new public API is added without a named type, a bounded capacity, a
  zero-allocation contract, and an ADR when the contract is observable.

## 1. How to use this guide

### 1.1 Human workflow

1. Read the inventory in section 0 and pick the next open milestone.
2. Work milestones in the order in section 10. Do not start a later milestone
   while an earlier one has missing required evidence.
3. A limit closes in exactly two ways:
   - it is fixed and verified, or
   - it is re-declared with a linked reason, raw evidence, and an explicit
     restoration criterion.
   No limit closes by deleting a test, skipping a gate, lowering a threshold,
   or writing a claim without artifacts.
4. Update `CHANGELOG.md`, `docs/`, and the relevant ADR in the same change that
   closes or re-declares a limit.
5. Do not modify or move `v2.1.6`.
6. Treat 100 MB as a logical streaming requirement, not a reason to allocate a
   100 MB buffer. Memory stays bounded by the configured slab and transfer
   buffer.

### 1.2 Agent workflow

Every milestone follows the repository agent sequence:

| Phase | Agent | Required output |
| :--- | :--- | :--- |
| Architect | `architect` | Scope, assumptions, affected ownership boundaries, acceptance criteria, file list |
| Implementer | `developer` plus the domain specialist (`transport_io`, `http_protocol`, `crypto_tls`, `build_vendor`, `quic_h3`, `verification`, ...) | Diff, commands run, raw results, unresolved questions |
| Reviewer | `reviewer` | Independent correctness/security/compatibility/convention review with file and line references |
| Integrator | `integrator` | Combined diff check, required verification evidence, delivery summary |

Rules:

- Do not advance past a phase while its required output is missing.
- Never claim an unrun check passed. Report exact commands and their output.
- Keep edits to shared files serialized; parallelize only independent slices.
- Do not add `TODO`, `FIXME`, `XXX`, or `HACK` markers to the repository.
  This document is the tracker.
- For a maintained-dependency change, read `docs/dependency_forks.md` first.
  The integration branch is append-only; the mirror is read-only; pin only a
  full 40-hex integration commit.
- For a codebase question, use the project knowledge graph before raw grep and

### 1.4 The evidence contract

Every benchmark or load result used to close a limit stores, in one directory:

- source URL and retrieval time of every tool used;
- exact uWebZockets commit or tag, Zig version, dependency pins, and
  `flake.lock` hash;
- CPU model, core count and quota, affinity policy, SMT state, kernel version,
  governor, and memlock limit;
- libxev backend (`io_uring`, `epoll`, or `kqueue`), optimization mode, worker
  count;
- load generator version, threads, connections, streams, duration;
- HTTP version, keep-alive, TLS version, compression settings;
- exact request and response bytes;
- warmup, sample count, statistic, and spread;
- success and error rates plus CPU, RSS, and tail latency;
- listener ownership and run-status evidence.

Never combine numbers from different systems, backends, or host cohorts into
one ratio. Treat a changed backend, kernel, worker count, or workload as a new
cohort and a new series. Never edit generated benchmark output by hand.

Use the three-file policy under `benchmarks/results/<series>/<date>/`:
an archive of raw output, a `README.md` summary, and a machine-readable
manifest. A result without raw output is not evidence.

### 1.5 Never do these

- Do not disable leak detection, `halt_on_error`, or a sanitizer check.
- Do not delete, skip, or weaken a test to make a graph green.
- Do not change benchmark window sizes, buffer caps, or worker counts before a
  probe shows that the cost is real.
- Do not publish a number that a reviewer cannot reproduce from raw artifacts.
- Do not modify the HttpArena repository data by hand.
- Do not replace an accepted socket or read result with `Canceled` without a
  documented disposal rule.
- Do not move or delete the `v2.1.6` tag or release.
- Do not use ephemeral development certificates for recorded measurements.
- Do not push to the upstream libxev, lsquic, or h1spec repositories.
- Do not add a local patch, overlay, or CI `patch` step for a maintained
  dependency.
- Do not claim live WebTransport, kTLS integration, or Windows runtime support
  before the matching gate has passed.

### M1-1 Response streaming audit (S-1 response half)

**Current state:** shipped. `Response.begin_stream` arms a drain-driven
producer; `write_chunk` writes HTTP/1 chunked framing, HTTP/2 DATA, or HTTP/3
stream bytes; `end_chunks` terminates. Every transport resumes a producer that
returned `.pending`. `src/http/streams.zig` provides the standalone byte-stream
primitives.

`TODO.md` names `src/http/stream.zig` for this surface; the shipped module is
`src/http/streams.zig`. Do not create a duplicate module or rename the public
surface just to match the plan.

**Required behavior:**

- Preserve the public API and the `.pending` / `.done` contract.
- A producer may return `.pending` at any chunk boundary and must be resumed
  exactly once per drain opportunity.
- A zero-length chunk is a no-op, not a terminal chunk.
- HEAD, 204, 304, and other bodyless responses must not stream a body.
- A producer error, peer reset, or stream reset aborts exactly once and
  releases its slot and timer state.

**Checklist:**

- [ ] Add a transport matrix test for HTTP/1, TLS HTTP/1, HTTP/2, and HTTP/3
      with producers that emit 1-byte, 16 KiB, and 64 KiB chunks and return
      `.pending` at least once.
- [ ] Add a close/reset test for each framed transport; assert no double
      completion and no leaked slot.
- [ ] Add a test that a producer which returns `.done` without `end_chunks`
      still fails closed.
- [ ] Check the hot path for allocation, locks, and retained caller slices;
      record the audit in the PR.
- [ ] Document the backpressure contract in `docs/http.md` and link it from
      `docs/api.md`.
- [ ] Run the HTTP/1 and HTTP/2 regression suites and the sanitizer gate.

**Acceptance:** the existing streaming API passes the transport matrix, no
public API changes, no allocation on the chunk path, and the contract is
documented.

**Owners:** `http_protocol` and `transport_io`; `verification` runs the matrix.

### M1-2 Static file delivery for framed transports (S-3 and S-4)

**Current state:** `static_files` already provides ETag, `Last-Modified`, 304,
byte ranges, `If-Range`, HEAD, MIME mapping, path confinement, and plaintext
`sendfile`. TLS, HTTP/2, and HTTP/3 decline `send_file` and fall back to a
full-file user buffer; a file larger than that buffer returns 413. There is no
`.gz`/`.br` sidecar negotiation. kTLS is a standalone helper; the pinned
BoringSSL has no supported key handoff.

**Required behavior:**

- Stream a file body through the existing producer contract on TLS, HTTP/2, and
  HTTP/3. Use a fixed, route-owned transfer buffer; do not allocate per request.
- Preserve exact `Content-Length`, HEAD, ranges, `Content-Range`, 304, and
  `Last-Modified` semantics.
- Keep plaintext `sendfile` as the preferred path.
- Add precompressed sidecar negotiation for `file.ext.br` and `file.ext.gz`.
  Honor `Accept-Encoding` quality values, including `identity` and `q=0`.
- Emit `Vary: Accept-Encoding` and `Content-Encoding` when a sidecar is chosen.
  The selected representation gets its own strong ETag and `Last-Modified`.
- Do not serve a stale sidecar. Compare sidecar and source modification times
  and fall back to the source when the sidecar is older.
- A range request applies to the selected representation. If the implementation
  cannot prove exact encoded ranges, serve the identity representation for
  ranges and document that choice.
- kTLS remains out of scope for 2.2.0 unless a supported key-handoff API is
  available. Record the decision and keep v3.5.0 SB-31 as the owner.
- `io_uring_prep_splice` is optional. Add it only if a probe shows a repeatable
  benefit over `sendfile`; otherwise record "measured, not needed".

**Checklist:**

- [ ] Add the bounded file producer and use it when `send_file` declines and the
      file exceeds the current buffer.
- [ ] Remove the large-file 413 for framed transports without weakening the
      path-confinement or bodyless-response rules.
- [ ] Add a pure `Accept-Encoding` negotiation helper. Keep it allocation-free
      and independent of I/O.
- [ ] Add sidecar selection with ETag/Last-Modified/`Vary`/`Content-Encoding`
      and stale-sidecar fallback.
- [ ] Add tests for: file larger than the buffer over TLS, HTTP/2, and HTTP/3;
      HEAD; single range; `If-Range`; 304; gzip and br quality values; missing
      and stale sidecars; path traversal; unsupported encodings.
- [ ] Add or update the static profile example and record `static-h2`,
      `static-h3`, and `static-tls` artifacts.
- [ ] Record the kTLS and splice decisions in `docs/roadmap.md` or the relevant
      ADR; do not imply integration that is not present.

**Acceptance:** large static assets stream on all transports; validators,
ranges, sidecars, and content codings are correct; no hot-path allocation;
`static-*` evidence is archived; kTLS and splice decisions are dated.

**Owners:** `http_protocol`, `transport_io`, and `verification`;
`crypto_tls` reviews the kTLS boundary.

### M1-3 100 KiB TLS echo (S-5)

**Current state:** `write_tls_parts` splits arbitrary plaintext into 16 KiB TLS
records and accounts for record overhead. The 16 KiB value is a per-record cap,
not a total-body cap; multi-record framing already exists. The default
per-connection write queue is 64 KiB, so a single 100 KiB response write cannot
fit. The response producer path can write bounded chunks without enlarging the
queue.

**Required behavior:**

- A 100 KiB response body must complete with multiple TLS records and bounded
  queue occupancy.
- Do not raise the 16 KiB record cap or the 64 KiB write queue to pass the
  benchmark. Chunk the producer instead.
- The echo path must not allocate and must not retain caller buffers after the
  producer returns.

**Checklist:**

- [ ] Add a TLS loopback test that sends a 100 KiB body through `begin_stream`
      and asserts exact bytes, at least seven 16 KiB records, and no queue
      overflow.
- [ ] Add the equivalent HTTP/1 plaintext control for comparison.
- [ ] Add an example or benchmark route if the repository owns one; otherwise
      record the exact external adapter change needed for `8gbit`.
- [ ] Run the HttpArena `8gbit` profile and archive the raw output, or
      re-declare the evidence with the blocker and a dated restoration
      criterion.
- [ ] Check the hot path for allocation and retained slices.

**Acceptance:** 100 KiB TLS echo passes with multi-record framing and no queue
growth; `8gbit` evidence exists or is explicitly re-declared.

**Owners:** `transport_io` and `crypto_tls`; `verification` runs the evidence.

## 4. M2 — Request streaming and incremental multipart

**Objective:** stop buffering complete uploads. A handler or sink must be able
to consume a 100 MB request with bounded memory on every transport, and the
multipart parser must operate on arriving chunks instead of a complete body.

**Files:**

- `src/http/parser.zig`, `src/http/request.zig`, `src/http/multipart.zig`
- `src/core/tcp.zig`, `src/http2/server.zig`, `src/quic/stream.zig`
- `src/router/config.zig`, `src/router/app.zig`, `src/router/radix.zig`
- `src/tests/http_tests.zig`, `src/tests/http2_server_tests.zig`,
  `src/tests/quic_tests.zig`, `src/tests/fuzz_main.zig`
- `docs/adr/0008-request-body-streaming.md`, `docs/http.md`, `docs/api.md`,
  `CHANGELOG.md`

### M2-1 Request streaming design and contract (S-1 request half)

**Current state:** the parser stores the complete body in the per-connection
request buffer, dispatches only after the body completes, and exposes it as
`Request.body`. `max_body_size`, `max_h2_body_size`, and `max_h3_body_size`
bound the storage. Synchronous handlers cannot wait for later bytes, and the
existing `AsyncResponse` token is a response-completion mechanism, not a
general coroutine.

**Design requirement:** write and accept
`docs/adr/0008-request-body-streaming.md` before code. The ADR must choose one
public contract:

- Candidate A (recommended): an opt-in route-level body sink with
  `begin`/`chunk`/`end` callbacks, a caller-owned context, and a bounded
  per-connection state slot. The parser feeds chunks as they arrive and pauses
  reads when the sink backpressures.
- Candidate B: hand a `ReadableByteStream` to an asynchronous upload handler and
  resume it on drain. Choose this only if it can be implemented without a
  coroutine runtime or an unbounded continuation list.

The ADR must also define:

- middleware ordering and the fact that streaming middleware sees headers
  before the body;
- the behavior of body-reading helpers (`text`, `bytes`, `json`, `form`,
  `multipart`) in streaming mode;
- backpressure, cancellation, early peer close, `Expect: 100-continue`, and
  trailers;
- the exact per-route and per-connection capacity, plus the refusal error when
  it is exhausted;
- source compatibility for existing buffered handlers.

**Checklist:**

- [ ] Write and review ADR 0008; link it from `docs/http.md` and `docs/api.md`.
- [ ] Add named public types for the chosen contract. No `anytype` in the public
      API and no inline anonymous callback structs.
- [ ] Extend the parser with a streaming mode that emits body bytes instead of
      copying them into `Request.body`. Enforce `Content-Length` and chunked
      decoding with the same strictness as the buffered path.
- [ ] Wire the mode through HTTP/1, TLS HTTP/1, HTTP/2 DATA, and HTTP/3 stream
      input. Keep HTTP/1 pipelining suspended while an upload is in flight.
- [ ] Pause reads on sink backpressure and resume on drain. A sink error,
      reset, or close must cancel exactly once.
- [ ] Keep the existing buffered path as the default. A route that does not opt
      in must behave exactly as it does today.
- [ ] Add tests for: split headers and body, split chunk CRLF, chunk
      extensions, `Expect: 100-continue`, early peer close, sink error, body
      over the configured cap, 100 MB logical stream, HTTP/2 flow control, and
      no allocation on the chunk path.
- [ ] Update capacity documentation and the package-consumer test if the public
      surface changes.

**Acceptance:** ADR 0008 is accepted; a 100 MB upload streams through every
transport with bounded memory; existing handlers and body helpers are
source-compatible; no hot-path allocation.

**Owners:** `http_protocol`, `transport_io`, and `dx_router`; `architect`
reviews the ADR; `verification` runs the matrix.

### M2-2 Incremental multipart parser (S-2)

**Current state:** `src/http/multipart.zig` parses a complete `[]const u8`
body. It handles RFC 2046 preamble/epilogue, RFC 7578 `form-data`, quoted
`name`/`filename`, boundary-prefix rejection, and SIMD delimiter search. It is
zero-allocation and fuzzed, but it is not an incremental state machine.

**Required behavior:**

- Parse arbitrary chunk boundaries without buffering the whole part.
- Borrow only the bytes needed for metadata; stream part data to a sink.
- Enforce a maximum boundary length of 70 bytes, bounded part headers, a
  bounded part count, and a caller-selected total limit.
- Reject truncated bodies, missing final boundaries, malformed headers,
  boundary-prefix sequences, duplicate `Content-Disposition`, missing `name`,
  and CR/LF injection in metadata.
- Keep the existing full-body `Request.multipart()` API for compatibility.

**Checklist:**

- [ ] Add a `StreamingParser` state machine with states for preamble, boundary,
      headers, body, and epilogue. Carry at most `boundary.len + 4` bytes across
      chunk boundaries.
- [ ] Add a named sink contract, for example `begin_part(PartMeta)`,
      `write_chunk([]const u8)`, and `end_part()`. The parser performs no I/O.
- [ ] Add an optional file sink helper that writes with `std.Io.File` and
      propagates errors. The caller owns the path buffer and file lifetime.
- [ ] Integrate the parser with the request-streaming sink from M2-1 so a
      multipart upload never materializes in `Request.body`.
- [ ] Extend the fuzz target with adversarial chunk splits and add seeds for
      split boundaries, preamble/epilogue, truncated parts, many parts, and
      large parts.
- [ ] Add tests for a 100 MB upload, a part larger than the old body cap, a
      boundary split at every byte, a slow sink, and a sink error.
- [ ] Add a benchmark or deterministic throughput comparison against the
      full-body parser on the same input; no allocation.

**Acceptance:** a 100 MB multipart upload streams to a sink with bounded memory;
the full-body API still works; malformed inputs fail closed; fuzz and sanitizer
runs are clean.

**Owners:** `http_protocol`; `verification` owns fuzz and the streaming matrix.

## 10. Sequencing

1. M0 baseline.
2. M1 response, static, and TLS payload closure. M1-1 and M1-2 can overlap;
   M1-3 needs the producer path from M1-1.
3. M2 request streaming and multipart. Start the ADR during M1, but land the
   parser changes after the response and static work so the shared transport
   files stay serialized.
4. M3 dependency gates. The lsquic and h1spec gates are independent and can run
   in parallel.
5. M4 WebTransport, after M3, because it changes the lsquic pin and must not be
   combined with an unrelated dependency refresh.
6. M5 structural ownership, after the feature files stabilize. Do not run M5
   concurrently with edits to `src/router/app.zig` or `src/core/tcp.zig`.
7. M6 evidence, platform, and decisions, after the code and pin freeze. C5 and
   C6 documentation can start earlier if their files are disjoint.
8. M7 release.

M1 and M2 may run beside M3 as long as the dependency work does not touch the
same files. Never combine a dependency pin with a feature change, except for
the ledgered lsquic server WebTransport commits in M4. Each milestone gets its
own reviewable PR and raw evidence.

Critical path: M0 -> M3 (lsquic baseline) -> M4 -> M6 (gates and evidence) ->
M7. M1 and M2 are the largest library slices and should start early.
